八、安全性说明

1. 如何防止普通用户删除数据

（1）数据库层面：通过创建只读用户，仅授予 SELECT 权限，不授予 DELETE、UPDATE、INSERT 权限。

-- 创建只读用户
CREATE USER readonly_user WITH PASSWORD 'secure_password';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_user;

（2）应用层面：在 Flask 应用中实现角色权限控制（RBAC），普通用户角色无法访问删除接口。后端路由增加权限校验装饰器，非管理员请求删除操作时返回 403 Forbidden。

（3）SQLite 实现：本系统使用 SQLite，可通过应用层逻辑限制：删除操作仅允许管理员角色执行，前端对普通用户隐藏删除按钮，后端对删除请求进行身份验证。

2. 如何限制用户只能查询数据

（1）数据库层面：创建数据库视图，仅将视图的 SELECT 权限授予普通用户，不授予基表的写权限。

-- 授予视图查询权限
GRANT SELECT ON sold_items_view TO readonly_user;
GRANT SELECT ON unsold_items_view TO readonly_user;

（2）应用层面：使用参数化查询防止 SQL 注入，对所有用户输入进行验证和转义；根据用户角色动态渲染页面，普通用户仅显示查询相关功能。

九、并发与恢复说明

1. 两个用户同时购买同一商品会出现什么问题

  • 脏读/不可重复读：用户A读取商品状态为"未售出"，此时用户B也读取到"未售出"，两人同时发起购买。
  • 数据不一致：两个订单同时插入 orders 表，同一 item_id 出现两次，违反"每个商品最多只能被交易一次"的业务规则。
  • 超卖问题：商品的 status 可能被两次更新为 1，但实际产生了两笔订单，导致一个商品被卖给两个买家。

2. 如何解决（加锁/事务）

（1）使用数据库事务：将"查询商品状态→插入订单→更新商品状态"封装在一个事务中，确保原子性。

BEGIN TRANSACTION;
SELECT status FROM item WHERE item_id = ?;
INSERT INTO orders (...) VALUES (...);
UPDATE item SET status = 1 WHERE item_id = ?;
COMMIT;

（2）SQLite 中的实现：SQLite 默认使用 SERIALIZABLE 隔离级别，通过 conn.execute("BEGIN IMMEDIATE") 获取写锁，确保同一时刻只有一个写事务。本系统在购买操作中使用 try/commit/rollback 模式保证事务完整性。

3. 如果系统崩溃，如何恢复订单数据

（1）数据库事务的原子性保证：如果崩溃发生在事务执行过程中（未 COMMIT），数据库重启后会自动 ROLLBACK 未完成的事务，数据回到事务开始前的一致状态。

（2）WAL（Write-Ahead Logging）机制：SQLite 默认使用 WAL 模式，所有修改先写入日志文件，再写入数据库。崩溃后重启时，SQLite 自动执行恢复流程。

（3）定期备份：可通过 sqlite3 campus_trade.db ".backup backup.db" 定期备份数据库文件。

（4）应用层恢复：本系统在购买操作中使用 try/except/rollback 模式，任何异常都会回滚事务，保证数据一致性。
